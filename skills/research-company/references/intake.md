# 方向选择与状态

## 初次输入

在公司身份唯一时，用一轮简短选择决定方向。开场可以是：

> 已收到 tinycontrol.pl。先选调研方向；选择“默认”即可按全面了解、全部产品、快速筛选开始。

### Q1 调研目的，单选

1. 全面了解与筛选（默认）：业务、角色、产品与合作潜力。
2. 产品合作与首次联系：优先找具体匹配、采购环节与联系切入点。
3. 同类公司与生态拓展：优先确认生态位置并发现相邻客群。

### Q2 产品重点，多选

1. LoRa 模组
2. 开发板
3. 气象站
4. 传感器
5. 采集器 / 网关
6. 全部上述产品（默认，与 1–5 不重复累计）

允许用户补充自有产品/供应商。选择“全部”时将产品类别保存为前五项。
选择采集器/网关时分别判断采集与网络接入的采购机会，不将其视为同一设备。

### Q3 调研深度，单选

1. 快速筛选（默认）：先判断是否值得联系，六个核心问题均覆盖。
2. 深入调研：增加技术资料、案例、触发信号、采购路径与同行。

不要承诺固定耗时或必定找到指定数量的来源。默认中文报告，首次联系草稿默认英文；用户给出其他语言时覆盖默认。

## 控件限制与文本回退

- 按工具实际 schema 控制问题/选项数量和多选参数。
- 真正支持多选且最多四个选项时，把 Q2 拆成两题：先多选“模组、开发板、气象站、其他设备”；选择“其他设备”后再多选“传感器、采集器、网关”。全类别用户可直接回复“全部”，不要额外追问。
- 可用工具只支持单选时，用原生工具收集 Q1/Q3；Q2 用编号多选消息，或一次文本问卷完成三个问题。不要用三个单选伪装多选；不要创建不可提交的 HTML 表单。
- 当前宿主限制选项为 2–3 个时，Q1 保持三项，Q3 保持两项；Q2 走文本多选。原生工具调用受宿主更高优先级约束时，使用文本回退。
- 文本示例：“回复 `目的2；产品1,3,4；深度1`，或回复 `默认`。”解析自然语言与编号均可。
- 用户部分回答时，对缺失的非关键选项采用默认值并在调研开始前用一句话说明。
- 用户已说“找 LoRa 模组采购机会、深入”时，不再问这三个已确定的项目。
- 不在每轮结尾重新弹出问卷；用户选项会持续到更换公司或主动修改。

## 身份歧义

- 域名或官网 URL：提取域名，核对公司及站点说明。不要因只看到品牌就杜撰法人名。
- 企业邮箱：保留域名，删除个人用户名后搜索公司；不根据邮件用户名推断其职务。仅在报告确实需要且用户同意保留联系人时使用完整邮箱。
- 公共邮箱：例如 gmail.com/outlook.com 等不能唯一定位雇主，要求公司名称或官网。不要把邮箱服务商当目标公司。
- 同名公司：给出最多三个可验证的候选，附地区/官网，让用户选择一次。
- 输入链接可访问失败：搜索官方域名索引和公开材料，注明访问限制；不要求用户反复测试同一个网络错误。

## 状态记录

维护以下会话字段即可，无需持久化个人信息：

```json
{
  "target_input": "tinycontrol.pl",
  "company_identity": {"name": null, "domain": "tinycontrol.pl", "confirmed": false},
  "purpose": "overview",
  "product_focus": ["lora-modules", "development-boards", "weather-stations", "sensors", "loggers", "gateways"],
  "depth": "quick",
  "supplier_profile": "seeed",
  "report_language": "zh-CN",
  "outreach_language": "en",
  "user_context": null
}
```

purpose 可为 overview / cooperation / ecosystem。supplier_profile 可为 seeed / user-provided。
不要向用户展示内部状态字段，除非其要求 JSON 导出。
